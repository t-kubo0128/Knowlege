1全体像を把握する

PC環境構築で躓く原因の多くは、「各技術が何のために存在するのか」が見えていないことです。まず全体像を掴みましょう。

アナロジー：会社の入館システムで考える

あなたのPCが「会社のビル」だと想像してください。

SSL/TLS証明書 = 入館証の真贋確認。偽の入館証を持った人を排除します。
SSH = 社員専用の裏口。一般客とは別の安全な通路で出入りします。
プロキシ = 受付担当。すべての出りを一元管理し、規則に従って中継します。
パッケージマネージャー = 備品調達係。必要なものを自動で取り寄せてくれます。

技術役割躓きやすいポイント
SSL/TLS証明書通信相手の正体を確認し、通信を暗号化する自己署名証明書、社内CA、期限切れ
SSHサーバーに安全にログインする鍵の場所、known_hosts、パーミッション
プロキシインターネットアクセスを中継する認証、NO_PROXY設定、HTTPS対応
パッケージマネージャーソフトウェアを自動インストールするPATH設定、依存関係、権限

2パッケージマネージャー

パッケージマネージャーは、ソフトウェアを「探して・ダウンロードして・インストールして・更新する」作業を自動化するツールです。CLIで操作することで、再現性のある環境構築が可能になります。

Mac: Homebrew

Mac事実上の標準パッケージマネージャーです。インストール済みと推定されますが、確認方法は以下です。

macOS 
# Homebrewがインストールされてるか確認
brew --version

# インストールされていない場合のみ実行
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# インストール後、PATHを通す（M1/M2/M3 Macの場合）
echo 'eval "$(/opt/homebrew/bin/brew shellenv)"' >> ~/.zprofile
eval "$(/opt/homebrew/bin/brew shellenv)"
Intel Mac vs Apple Silicon Mac

Intel Macでは /usr/local、Apple Silicon Mac（M1/M2/M3/M5）は /opt/homebrew にインストールされます。PATHが違うため、混同しないよう注意してください。

Windows: 3つの選択肢

Windowsには複数のパッケージマネージャーがあります。用途に応じて使い分けます。

Windows
ツール特徴おすすめ用途
wingetMicrosoft純正。Windows 11では標準搭載。一般的なソフト（Chrome、VS Codeなど）
scoopユーザーディレクトリにインストール。管理者権限不要。開発ツール（Git、Node、Pythonなど）
chocolatey最も豊富なパッケージ数。企業利用も多い。業務アプリの一括導入

winget（Windows公式）

# インストール済みか確認（Windows 10 20H2以降 / Windows 11）
winget --version

# ソフトを検索
winget search git

# インストール
winget install --id Git.Git -e --source winget

# アップデート
winget upgrade --all

Scoop（開発者向け）

# インストール（PowerShellで実行）
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser
Invoke-RestMethod -Uri https://get.scoop.sh | Invoke-Expression

# よく使うbucket（パッケージ集）を追加
scoop bucket add extras

# インストール例

PowerShell実行ポリシーについて

Set-ExecutionPolicy は「PowerShellスクリプトの実行を許可する」設定です。セキュリティ上の設定なの、社内PCでは変更が制限されている場合があります。その場合はIT部門に確認してください。

3SSL/TLSと証明書

SSL/TLS（Secure Sockets Layer / Transport Layer Security）は、インターネット通信を暗号化する技術です。「https://」のサイトはすべてこれを使っています。

アナロジー：封筒と証明書

HTTP通信は「はがき」、HTTPS通信は「封筒に入った手紙」です。封筒を開けられるのは宛先の相手だけです。

証明書は「封筒に貼られたホログラムシール」のようなものです。本物のシールが貼ってあれば、その手紙は本当にその会社から来たと信じられます。

証明書の種類

種類説明躓きやすさ
公開CA証明書DigiCert、Let's Encryptなどが発行。ブラウザが自動で信頼。低（基本自動）
社内CA証明書企業が独自に運用する証明書。社内システムで使用。高（手動インストールが必要）
自己署名証明書個人やテスト用途で自分で発行。誰も信頼しない。高（明示的に信頼設定が必要）

社内CA証明書のインストール（企業環境で必須）

多くの企業では、社内のプロキシサーバーがSSL通信を「中継・検査」します（SSLインスペクション）。この際、社内CAが発行した証明書をPCが信頼していないと、ブラウザやCLIツールがエラーを出します。

macOS 
# 社内CA証明書をダウンロード（IT部門から入手）して、システムキーチェーンに追加
sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ~/Downloads/company-ca.crt

# HomebrewでインストールしたGit/curlに証明書を認識させる
git config --global http.sslCAInfo /path/to/company-ca.crt
Windows 
# PowerShell（管理者権限）で実行
Import-Certificate -FilePath "C:\Users\YourName\Downloads\company-ca.crt" -CertStoreLocation Cert:\LocalMachine\Root

# Git for Windowsに証明書を認識させる
git config --global http.sslCAInfo "C:\Users\YourName\Downloads\company-ca.crt"
「一時的にSSL検証を無効にする」設定は避ける

git config --global http.sslVerify false や curl -k は、セキュリティを完全に無効化します。一時的な回避策として使われることがありますが、本質的な解決にはなりません。社内CA証明書を正しくインストールする方が正攻法です。

GitのSSLエラー対処フロー

  1. エラーメッセージを確認：unable to get local issuer certificate なら証明書問題
  2. 社内CA証明書をIT部門から入手する
  3. OSの証明書ストアにインストールする
  4. Gitに証明書パスを教える（http.sslCAInfo）
  5. プロキシ設定も併用している場合は、そちらも確認する

4SSH（Secure Shell）

SSHは、リモートサーバーに安全に接続するためのプロトコルです。GitHubやGitLabへの接続、社内サーバーへのログインなどで使います。

アナロジー：鍵付きポスト

SSHは「鍵付きの私人書ポスト」です。公開鍵は「ポストの投入口」（誰でも見られる）、秘密鍵は「ポストの鍵」（絶対に他人に見せない）です。サーバーに公開ない）です。サーバーに公開鍵を預けておき、接続時に秘密鍵で「自分だ」と証明します。

SSH鍵ペアの生成

現代の標準は Ed25519 アルゴリズムです。古いシステムで対応していない場合のみ RSA を使います。

macOS / Windows共通 
# Ed25519で鍵ペアを生成（推奨）
ssh-keygen -t ed25519 -C "[email protected]"

# 保存場所の確認（デフォルトでEnter）
# パスフレーズは設定推奨（空でも可）

# 公開鍵の内容を表示（この内容をGitHub/GitLabに登録）
cat ~/.ssh/id_ed25519.pub
ssh-ed25519 AAAAC3NzaC... [email protected]

GitHubへの公開鍵登録

  1. GitHubにログイン → 右上アイコン → Settings
  2. 左メニュー「SSH and GPG keys」→「New SSH key」
  3. Titleにわかりやすい名前（例："MacBook-Pro"）を入力
  4. Key欄に ~/.ssh/id_ed25519.pub の内容を貼り付け
  5. 「Add SSH key」をクリック

SSH接続テスト

# GitHubへの接続テスト
ssh -T [email protected]
Hi username! You've successfully authenticated...

# 失敗した場合は詳細ログを確認
ssh -vT [email protected]

SSH configファイル（複数の鍵を管理）

会社用と個人用で別々の鍵を使いたい場合、~/.ssh/config で管理します。

# ~/.ssh/config
Host github-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_personal

Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work

Host gitlab-work
    HostName gitlab.company.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
    # 社内プロキシ経由の場合
    ProxyCommand nc -X connect -x proxy.company.com:8080 %h %p

known_hostsとは

初めて接続するサーバーにSSHでアクセスすると、「本当にこのホストを信頼しますか？」と聞かれます。Yesと答えると、サーバーの「指紋」が ~/.ssh/known_hosts に保存されます。次回からは自動で信頼されます。

known_hostsエラー

サーバーが再インストールされたり、IPが変わったりすると、保存された指紋と一致しなくなり、WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED! というエラーが出ます。ssh-keygen -R ホスト名 で古いエントリを削除すれば解決します。

5プロキシ設定

企業環境では、インターネットへのアクセスが「プロキシサーバー」を経由するのが一般的です。プロキシを正しく設定しないと、ほとんどのCLIツールが外部と通信できません。

アナロジー：会社の受付

プロキシは「会社の受付担当」です。社員（あなたのPC）が外に電話をかけるとき必ず内線プロキシ）を通します。受付が「誰ですか？」と確認するので、認証情報が必要な場合もあります。

環境変数での設定

多くのCLIツールは、以下の環境変数を自動的に読み取ります。

変数名用途例
HTTP_PROXYHTTP通信のプロキシhttp://proxy.company.com:8080
HTTPS_PROXYHTTPS通信のプロキシhttp://proxy.company.com:8080
NO_PROXYプロキシを経由しないホストlocalhost,127.0.0.1,.company.com
macOS 
# ~/.zshrc に追加（Zshの場合）
export HTTP_PROXY="http://proxy.company.com:8080"
export HTTPS_PROXY="http://proxy.company.com:8080"
export NO_PROXY="localhost,127.0.0.1,.company.com,10.0.0.0/8"

# 反映
source ~/.zshrc
Windows 
# PowerShellで一時的に設定（現在のセッションのみ）
$env:HTTP_PROXY = "http://proxy.company.com:8080"
$env:HTTPS_PROXY = "http://proxy.company.com:8080"

# 永続的に設定（システム環境変数）
[System.Environment]::SetEnvironmentVariable("HTTP_PROXY", "http://proxy.company.com:8080", "User")
[System.Environment]::SetEnvironmentVariable("HTTPS_PROXY", "http://proxy.company.com:8080", "User")

認証付きプロキシの場合

ユーザー名とパスワードが必要なプロキシの場合、URLに埋め込みます。

export HTTP_PROXY="http://username:[email protected]:8080"
パスワードに特殊文字がある場合

@ や : などの特殊文字がパスワードに含まれる場合、URLエンコードする必要があります。例えば @ は %40 に置き換えます。セキュリティ上、パスードを平文で書きたくない場合は、.netrc ファイルや各ツールの認証キャッシュ機能を検討してください。

Gitのプロキシ設定

# Git専用のプロキシ設定
git config --global http.proxy http://proxy.company.com:8080
git config --global https.proxy http://proxy.company.com:8080

# 特定のホストだけプロキシを使わない
git config --global http.https://github.com.proxy ""

# 設定確認
git config --global --get http.proxy

NO_PROXYの書き方ルール

  • localhost, 127.0.0.1 : ローカル通信はプロキシ不要
  • .company.com : anything.company.com にマッチ
  • 10.0.0.0/8 : プライベートIP帯域全体を除外（CIDR表記）
  • github.com : 特定のドメインを直接接続

6Gitの初期設定

Gitは環境構築の中心ツールです。正しく設定しないと、コミット者名が正しく記録されなかったり、push/pullでエラーが出たりします。

最低限必要な設定

# ユーザー名とメールアドレス（必須）
git config --global user.name "Your Name"
git config --global user.email "[email protected]"

# デフォルトブランチ名をmainに
git config --global init.defaultBranch main

# エディタをVS Codeに設定
git config --global core.editor "code --wait"

# 設定確認
git config --global --list

社内環境での追加設定

# SSL証明書のパスを指定（社内CAがある場合）
git config --global http.sslCAInfo /path/to/company-ca.crt

# プロキシ設定
git config --global http.proxy http://proxy.company.com:8080

# 大文字小文字の扱いを厳密に（Mac/Windows間の互換性）
git config --global core.ignorecase true

# 改行コードを自変換（Windowsで作業する場合）
git config --global core.autocrlf true
# Mac/Linuxの場合は false または input
git config --global core.autocrlf input
Gitの設定ファイルの場所

グローバル設定は ~/.gitconfig（Mac/Windows共通）に保存されます。直接編集しても構いません。

7エディタ・IDEの設定

Visual Studio Code（VS Code）は現代の標準エディタです。社内環境では追加の設定が必要な場合があります。

VS Codeのプロキシ設定

VS CodeはOSのプロキシ設定を自動で読み取りますが、明示的に設定することもできます。

# VS Code内で Ctrl+Shift+P（Cmd+Shift+P）→ "Preferences: Open User Settings (JSON)"
{
  "http.proxy": "http://proxy.company.com:8080",
  "http.proxyStrictSSL": true,
  "http.proxySupport": "override"
}

拡張機能のインストール

社内プロキシ環境では、拡張機能マーケットプレイスへのアクセスが制限されることがあります。その場合：

  1. 拡張機能を .vsix ファイルとしてダウンロード（別のネットワークで）
  2. VS Codeで「Extensions」→「...」→「Install from VSIX」

8環境変数の管理

環境変数は、OSがプログラムに渡す「設定値」です。プロキシ設定、PATH、APIキーなどがここに入ります。

重要な環境変数一覧

変数名役割設定例
PATHコマンドを探すディレクトリ一覧/usr/local/bin:/usr/bin
HOME / USERPROFILEユーザーのホームディレクトリ/Users/username
HTTP_PROXYHTTPプロキシhttp://proxy:8080
HTTPS_PROXYHTTPSプロキシhttp://proxy:8080
NO_PROXYプロキシ除外リストlocalhost,127.0.0.1
NODE_EXTRA_CA_CERTSNode.js追加CA証明書/path/to/ca.crt
SSL_CERT_FILERuby/Python等のCA証明書/path/to/ca.crt
REQUESTS_CA_BUNDLEPython requestsライブラリのCA証明書/path/to/ca.crt

MacでのPATH設定

# ~/.zshrc に追加（Apple Silicon Mac + Homebrewの場合）
export PATH="/opt/homebrew/bin:$PATH"
export PATH="/opt/homebrew/sbin:$PATH"

# 自分でインストールしたツールのパスも追加
export PATH="$HOME/.local/bin:$PATH"

WindowsでのPATH設定

# PowerShellで追加（ユーザー環境変数）
$userPath = [System.Environment]::GetEnvironmentVariable("Path", "User")
[System.Environment]::SetEnvironmentVariable("Path", $userPath + ";C:\Tools\myapp", "User")

# 設定後、PowerShellを再起動しないと反映されない
PATHの順序が重要

PATHは「先に見つかったものが優先」されます。HomebrewでインストールしたGitが使われるようにするには、/opt/homebrew/bin が /usr/bin より前に来る必要があります。

9よくあるエラーと対処法

Git関連

エラーメッセージ原因対処法
unable to get local issuer certificate 社内CA証明書が信頼されていない 社内CA証明書をインストールし、http.sslCAInfo を設定
Failed to connect to github.com port 443 プロキシ設定がない/間違い HTTP_PROXY / HTTPS_PROXY を設定
Permission denied (publickey) SSH鍵がGitHubに登録されていない 公開鍵をGitHubに登録、ssh-add で鍵を読み込む
Could not resolve host DNSまたはネットワーク接続問題 プロキシ設定、VPN接続を確認

Homebrew関連

エラーメッセージ原因対処法
Command not found: brew PATHにHomebrewが含まれていない ~/.zshrc に /opt/homebrew/bin を追加
SSL certificate problem brewのcurlが社内CAを認識していない export SSL_CERT_FILE=/path/to/ca.crt

SSH関連

エラーメッセージ原因対処法
WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED サーバーの指紋が変わった ssh-keygen -R ホスト名
Bad owner or permissions SSH鍵のパーミッションが緩すぎる chmod 600 ~/.ssh/id_ed25519
Could not open a connection to your authentication agent ssh-agentが動いていない eval "$(ssh-agent -s)" → ssh-add

パケージインストール関連

エラーメッセージ原因対処法
Permission denied / EACCES インストール先への書き込み権限がない Scoop（Windows）を使う、または管理者権限で実行
Unable to download プロキシまたはSSL証明書問題 プロキシとCA証明書の両方を確認

10チェックリスト

新しいPCの環境構築時は、以下の順序で進めるとスムーズです。

ステップ1: 基本ツール

  • パッケージマネージャーをインストール（Mac: Homebrew / Windows: winget or scoop）
  • Gitをインストール
  • VS Codeをインストール
  • ターミナルを整える（Mac: iTerm2 or Warp / Windows: Windows Terminal）

ステップ2: ネトワーク設定

  • 社内CA証明書を入手・インストール
  • プロキシ設定を確認（HTTP_PROXY / HTTPS_PROXY / NO_PROXY）
  • Gitのプロキシ・SSL設定を確認
  • GitHubへのアクセステスト（ssh -T [email protected]）

ステップ3: 開発環境

  • プログラミング言語のランタイムをインストール（Node.js / Python / Javaなど）
  • 言語固有のパッケージマネージャーを設定（npm / pip / Mavenなど）
  • VS Code拡張機能をインストール
  • 必要に応じてDockerをインストール

ステップ4: 動作確認

  • git clone で社内リポジトリをcloneできる
  • npm install や pip install がプロキシ環境下で成功する
  • SSHでリモートサーバーにログインできる
  • VS Codeの拡張機能マーケットプレイスにアクセスできる
最後のポイント

環境構築で躓いたときは、「どのレイヤーで問題が起きているか」を切り分けることが重要です。ネットワーク層（プロキシ）なのか、認証層（証明書/SSH）なのか、ツール層（パッケージマネージャー）なのか。エラーメッセージをよく読んで、該当するセクションに戻って確認してください。
